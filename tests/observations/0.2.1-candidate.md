## epoll_socket_growth

**路由：**主技能 `embedded-debug-workflow`；辅助技能 `embedded-networking`（socket/fd 证据）；读取 `app-runtime.md` 与 `network-observation.md`。

10 分钟内 fd 从 120 增至 900、`CLOSE_WAIT` 同时累积，优先查应用的 socket 关闭路径。`CLOSE_WAIT` 表示对端 FIN 已到，而本端尚未关闭 socket；这支持“本地生命周期/清理未完成”的假设，但还不能仅凭快照确认泄漏。低 CPU 和没有 OOM 记录都不能排除该问题。

先保留故障现场，在相同负载下按时间重复采样同一目标 PID 和网络命名空间：比较 `ss -tanp state close-wait`、`/proc/$PID/fd` 链接与数量、`/proc/$PID/limits` 中该进程的 open-files 软硬限额，并保存原始日志和 `EMFILE` 等错误。工具或权限不支持时记为 unavailable。随后检查 epoll 的 EOF（`read` 返回 0）、`EPOLLRDHUP`/`EPOLLHUP`、错误、超时和取消分支是否注销并关闭 fd，以及 socket 所有权是否在回调/线程间一致。

**暂不先调高 fd 上限。**只有确认已触及进程限额或出现 `EMFILE`，并测得合法并发需求超过当前配置时，才评估相应服务限额；提高限额不会修复未关闭的 socket。验收应在同等负载下看到 fd 与 `CLOSE_WAIT` 回到稳定基线且不再持续增长。以上命令只是 TARGET 取证建议，未执行。

## epoll_thread_wait

**路由：**主技能 `embedded-debug-workflow`；读取 `app-runtime.md`、`debug-playbook.md`、`process-sampling.md`。没有 socket 队列、连接或 fd 异常证据，暂不转网络方向。

`pthread_cond_wait` 是等待点，不足以单独证明死锁；它也可能是正常空队列等待。先在同一时间窗保留目标 PID/TID、所有相关线程栈与状态、应用构建标识、请求 ID、队列长度/最老请求年龄，以及每个 enqueue/dequeue、signal/broadcast 的时间和返回码。重点确认“请求已入队”与“工作线程等待”指向同一队列、同一进程实例和同一时间点，排除请求之后已被其他消费者取走或日志先后错位。

然后走查实现：消费者是否在同一互斥锁保护下循环检查队列谓词（如 `while (queue.empty() && !stopping) pthread_cond_wait(...)`）；生产者是否在同一谓词/锁保护下更新队列并通知；生产者和消费者是否使用同一个 cond/mutex/队列实例；是否有错误返回、关闭/取消、重建对象或锁顺序分支跳过了通知或消费。记录所有 waiter 的栈和谓词状态，再用可控复现验证区分出的假设。不要仅凭等待栈提高线程优先级或增加线程数。当前无目标访问，不能判断是哪条路径导致等待。
