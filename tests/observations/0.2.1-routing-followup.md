## 路由选择

- **主技能：** `embedded-networking`。同一服务 fd 从 120 增至 900，且 `CLOSE_WAIT` 持续增加，已有明确 socket 生命周期证据；epoll 是应用事件循环背景。
- **辅助技能：** 暂无。没有线程等待栈或事件循环卡死证据，需要时再补 `embedded-debug-workflow`。
- **条件参考：** 已读取 `embedded-networking/references/network-observation.md`，因为技能对 fd 与 `CLOSE_WAIT` 累积明确指向该参考。

## 建议先查

`CLOSE_WAIT` 表示对端已发 FIN，本端 socket 尚未关闭。先让有权限的目标设备操作人员在相同负载下对同一个数字 PID 做多时点只读采样：确认 fd 数是否继续增长；核对 fd 链接中增长项是否为 socket，并和 socket 状态、连接存续时间及对端对应起来；同时记录该 PID 的 open-files 软/硬限额。检查应用收到 EOF（`recv` 返回 0）以及错误、超时、取消等退出路径是否都完成连接清理和 `close`，并核对 epoll 事件处理是否仍在推进。

**不要先调大 fd 上限。** 当前 900 不能单独证明已撞限或 fd 泄漏；需与该进程实际限额、同负载多时点趋势和 fd 类型一起判断。若增长主要是长期未关闭的 `CLOSE_WAIT` socket，应修复本端清理/关闭路径；提高限额只会推迟资源耗尽。只有确认合法峰值需求确实超过软限额后，再评估提高限额，并核实硬限额及部署配置。低 CPU 与没有 OOM 记录不能排除 fd 耗尽或连接清理问题。

目前只有题面提供的合成数据；没有目标板访问权限，因此未执行任何目标/主机诊断，也未验证根因或结果。
