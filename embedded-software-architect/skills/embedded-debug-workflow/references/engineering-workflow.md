# 通用嵌入式 Linux 工程流程

资料类型：通用工程方法。用于多步骤诊断、实现、移植或交付；简单问题在回答中记录必要要点即可，不强制生成整套报告或加载所有参考。厂商差异由对应领域的平台页与目标 SDK 补充。

## 1. 建立任务契约

先区分诊断、设计、实现和维护操作，再确认影响当前决策的最少信息：

| 项目 | 记录内容 |
|---|---|
| 目标 | 当前行为、期望行为、可复现输入/负载、成功与失败判据 |
| 环境 | HOST/TARGET/U-BOOT、目标架构与 ABI、硬件/板卡版本、运行软件及构建标识 |
| 可用条件 | 源码、SDK、工具链、日志、串口/板卡访问、可执行范围 |
| 约束 | 延迟/内存/功耗/存储等实际预算、数据持久性、兼容与恢复要求 |

仅收集会改变结论的信息。没有目标板时仍可分析源码、准备修复与离线检查；缺少 SDK 时仍可建立假设、接口契约和验证计划。涉及具体寄存器、引脚、电压、DMA 能力或厂商 API 时，缺失资料必须保留为未知。

主技能按用户目标和故障对象选择，依据新证据补辅助技能。应用使用 Qt、传输经过 Wi-Fi、进程运行在容器中，都不自动改变故障层的归属。先取得所用技能正文；目录存在或引用了一次名称不证明已经加载。

## 2. 固化证据与构建身份

记录证据来源、采样时间、执行环境、工具/命令及结果。区分自己采集、用户提供、推导和教学夹具。保存改变前的关键现场；不能先重启/重刷再把新状态当故障现场。

需要基础快照时，按 [取证工具说明](evidence-collection.md) 使用技能内的 collector。它只提供有限、非原子的快照，不代替根因分析；缺失项和截断项都影响覆盖范围。

需要构建时记录以下身份，而不是只记录一个发行版本号：

- 源码 revision、厂商 patch、板级 defconfig/config fragments、构建系统及参数。
- 编译器与 binutils/SDK 版本、target triple、sysroot、用户态 ABI 或目标内核构建树。
- 实际产物路径、构建标识/校验值及启动/部署选择，模块的匹配配置和符号版本要求。

主机架构不决定目标架构。ARM32、ARM64、RISC-V 或其他架构的镜像目标和 ABI 由实际 BSP 确认。构建失败或无法建立产物身份时，不宣称修改已经上板。

## 3. 用区分实验推进

对每个候选原因记录：它能解释哪些观察、不能解释什么、哪个最低成本检查能区分它与其他原因。先考虑只读观察，再选择任务确需且已授权的状态变更。

实验应给出预测与分支，例如：

| 观察 | 下一步 |
|---|---|
| 运行 DT 与预期源码不同 | 检查实际 DTB、overlay、bootloader 修改和产物选择，不能立刻改驱动 |
| 设备已枚举但 probe defer | 检查 provider 与资源依赖，不增加用户态忙等重试 |
| 进程被 memcg OOM 杀死 | 核对有效层级限制、计数和内存归属，不从 RSS 趋势宣布泄漏 |
| 媒体某阶段首次出现计数/时间戳差异 | 检查该阶段的协商、排队、处理与背压，再考虑下游/系统资源 |

尽量隔离一个因果变量。若修复需要成组修改来保持接口或生命周期不变量，说明其依赖关系，按一个完整修复验证；不把“单变量”理解为每次只能改一行代码。

## 4. 命令与示例契约

每个被实际采用的命令/片段应说明以下信息；现有文档未说明时，执行前补齐：

- **环境与前置条件**：在哪里执行，需要什么工具、版本、权限、文件和已确认目标。
- **形式**：可直接运行的命令、需替换参数的模板，或不构成完整程序的代码片段。尖括号/示意函数不能原样交给 shell/编译器。
- **预期观察**：输出哪些字段、返回值或事件；哪些现象支持/削弱假设。无输出、权限错误和功能正常是不同情况。
- **边界**：时长、字节数、采样间隔与日志位置；缺失功能的可用替代与未覆盖项。
- **副作用与失败路径**：是否写文件、启动进程/服务或改变设备状态，失败如何停止、保留证据和恢复。

不把未确认的私有 SDK 命令写成可复制的执行步骤。先发现目标镜像实际能力，查对应版本的源码/手册，再建立命令契约。普通工具也要确认 BusyBox/完整实现的选项差异。

## 5. 修改、验证与恢复

先确定需要保持的不变量，再实现最小完整变更：错误路径释放、异步访问退出、用户 ABI、缓冲区所有权、持久性和相关资源预算。设计测试应能发现行为错误，不能只匹配自己刚写的实现或文档句子。

验证按任务选择，不要求简单任务跑所有阶段：

1. 静态与主机逻辑检查：确认接口、配置、错误路径和可执行工具的行为。
2. 目标构建：使用匹配的 SDK/配置，保存命令、结果和产物身份。
3. 部署/启动：任务授权且可访问设备时，确认目标、恢复路径和新产物实际生效。
4. 功能与回归：相同输入/负载下验证修改目标、相关功能、失败恢复和资源趋势；长跑覆盖故障触发窗口。

恢复方案必须对应实际变更：配置修改保存原配置，镜像升级保留匹配恢复介质/旧产物，数据操作考虑备份和恢复。存在恢复说明不等于允许任意烧写或擦除。

## 6. 交付与维护

交付至少包含目标/变更、证据、版本/产物身份、已执行验证与关键结果、未执行项和下一步。待构建、待部署、待板测、失败分别标记；“没有新 error”不能代替功能验收。

多步骤工作可保留任务记录、证据索引、假设/实验、patch 和验证记录；简单任务用简短交付说明承载同样事实即可。依据与验证状态按 [资料与验证记录规范](validation-policy.md) 维护，避免将某块板的一次成功推广为整个芯片系列的保证。

## 依据与验证范围

本页是工程方法规范，不是某个平台的实测结果。构建身份和模块边界参考 [Linux Kbuild](https://docs.kernel.org/kbuild/index.html) 与 [外部模块构建](https://docs.kernel.org/kbuild/modules.html)；Devicetree 检查参考 [binding/schema 文档](https://docs.kernel.org/devicetree/bindings/writing-schema.html)。具体 API、工具与实验均需按当前目标确认。
